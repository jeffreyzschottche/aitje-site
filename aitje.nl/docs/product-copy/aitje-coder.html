Je beoordeelt de echte wijziging.

De agent werkt op de code die je aanwijst. In de diff zie je iedere gewijzigde regel. Het verslag vertelt wat is onderzocht, aangepast en getest. Je kunt per bestand commentaar geven en om een nieuwe poging vragen.

De pull request houdt het controleerbaar.

De goedgekeurde wijziging krijgt een plek in jullie Git-geschiedenis. Collega’s kunnen reviewen, bestaande CI kan de branch controleren en jullie eigen mergebeleid blijft de laatste stap. Een geopende pull request is nog geen automatische merge of publicatie.

Een agent krijgt afgebakende toegang.

De beheerder bepaalt welke repositories een developer mag gebruiken en of die zelf repositories mag verbinden. De agent werkt in een eigen werkmap. Voor toegang tot Git wordt de afgesproken verbinding ingericht, met tokens of een ondersteunde GitHub-login.

Het resultaat blijft van jullie team.

Code, tests en geschiedenis blijven gewone projectbestanden en Git-wijzigingen. Je kunt de wijziging verder aanpassen, afwijzen of via jullie eigen proces terugdraaien. Je hoeft het werk niet uit een chat te kopiëren om er een beoordeelbare wijziging van te maken.

Waar staat de database?

In de standaard appliance-installatie draait PostgreSQL als lokale dienst in de Coder-omgeving, met een eigen blijvend datavolume. Daar staan gebruikers, taken, planningen, reviewgegevens en de gebruikstellingen. Repositories en de werkmappen van de agent staan afzonderlijk op lokale opslag.

Wat staat op het apparaat van de gebruiker?

De browser bedient de web-app. Een terminal of editor kan met een persoonlijke sleutel het model op de box gebruiken; de bestanden van die client kunnen op de developerwerkplek staan. Bij taken via de Coder-webapp werkt de agent in zijn eigen werkmap op de box.

Wat houdt de beheerder in de hand?

Wie taken mag indienen of goedkeuren, welke repositories een developer mag gebruiken, welke modellen en tools toegankelijk zijn en welke limieten gelden. Budgetten, persoonlijke sleutels, supporttoegang en het logboek worden centraal beheerd.

Wat levert het AI Station op?

Rekenkracht en agentwerk in eigen beheer, met de repositories en reviewafspraken van het team. AITJE selecteert en test modellen en stelt de tools, rechten en wachtrij in. Je team kan bouwen zonder een externe tokenrekening voor lokale inferentie.

Als een externe AI-dienst een storing heeft

Het lokale model is beschikbaar zonder een externe model-API. Werken met lokaal aanwezige code kan doorgaan zolang box, lokale diensten en netwerk werken. Een nieuwe clone, pakketdownload of pull request bij een externe Git-dienst kan wel op die dienst moeten wachten. Lokale inference en externe Git-bereikbaarheid zijn afzonderlijke afhankelijkheden.

AITJE Coder is meer dan een model op een server. De beheeromgeving bepaalt wie in welke code mag werken, met welke werkwijze en hulpmiddelen, en binnen welke grenzen.

Jij bepaalt in welke code de agent mag werken.

Verbind een repository één keer en regel de toegang per repository: inloggen bij GitHub met een code, een token, of intrekken. Zonder toegang kan de agent een openbare repository lezen, maar geen pull request openen.

  • GitHub, GitLab en Gitea, ook een eigen Git-server met een eigen certificaat
  • Twee repositories koppelen voor taken die in beide werken
  • Toegangstokens staan versleuteld in de database

Eén account per persoon. Drie rollen.

Iedere developer krijgt een eigen account en een persoonlijke sleutel met eigen limieten. Uitnodigen gaat met een link of QR-code die 24 uur werkt. Elke beheerhandeling komt in gewone woorden in het logboek.

  1. DeveloperTaken indienen, de agent volgen en wijzigingen bekijken. Werkt met een eigen sleutel in de editor.
  2. ReviewerDaarnaast resultaten goedkeuren of afkeuren. Goedkeuren opent de pull request.
  3. BeheerderDaarnaast gebruikers, rollen, instellingen, supporttoegang en het logboek. De eigenaar van de box beheert accounts en sleutels.

Agent & review

01

Taken en meerdere repositories

Kies repository, startbranch, model en webzoeken. Werk waar nodig over gekoppelde repositories, in een eigen afgeschermde werkmap.

02

Live verloop en stoppen

Volg bestanden, commando’s, tests en fouten. Stop een taak met bevestiging; een vastgelopen herhaling krijgt een begrensde herstart.

03

Review per bestand

Bekijk wijzigingen naast of onder elkaar. Geef per bestand een oordeel en opmerking. Vergelijk runs of laat een aanpassing opnieuw uitvoeren.

04

Goedkeuring en Git

Een reviewer opent de pull request naar GitHub, GitLab of Gitea. GitHub-login met een code en een fork bij ontbrekend schrijfrecht worden ondersteund.

05

Wachtrij, planning en rondes

Orden of pauzeer de rij. Plan eenmalig, dagelijks, wekelijks of via cron. Start bij een push of GitHub-/Linear-issue en laat meerdere rondes doorwerken.

06

Voorrang voor interactief werk

Werk je zelf in een editor of chat, dan krijgt dat voorrang op de batchtaken. De wachtrij maakt zichtbaar wat wacht, draait of op review staat.

Tools & modellen

01

Terminal en editor

Configuraties voor Claude Code, OpenCode, Codex CLI, Aider, Cline, Roo Code, Kilo Code, Continue en Zed. Koppel via /connect of de CLI.

02

Lokale modellen en aanvullen

Een gekozen coder-model voor agentwerk en een klein model voor inline completion. De box biedt compatibele model-API’s, waaronder de native Messages-API.

03

Mijn sessies

Zie repository, branch, taaknaam, modelverzoeken en tokengebruik vanuit je tools. De sessietelling bewaart geen prompts of antwoorden.

04

Langere gesprekken

Ondersteunde clients kunnen context samenvatten voordat het venster vol raakt. Modelwissels, context en gelijktijdigheid stemmen we af op het geheugen.

05

Chat en hulpassistent

Stel een losse modelvraag bij Chat. Open met Ctrl J de ingebouwde hulpassistent voor taken, planning en uitleg; bevestigingsplichtige acties vragen je akkoord.

06

Desktop, mobiel en taal

Dezelfde web-app op een groot of klein scherm, licht of donker. Nederlands, Engels, Duits en Frans; telefoon en laptop zijn de toegang tot de box.

Team & budgetten

01

Accounts, rollen en uitnodigingen

Developer, reviewer en beheerder hebben eigen bevoegdheden. Nodig uit met een tijdelijke link of QR-code, wijzig rollen of blokkeer een account.

02

Repositorytoegang per persoon

Kies exact welke Git-URL’s een developer mag gebruiken en of die zelf repositories mag verbinden. Ingetrokken toegang blokkeert nieuw werk en verder streamen.

03

Persoonlijke sleutels en limieten

Beheer sleutels en stel modeltoegang, externe modellen, token- en aanvraaglimieten in. Editor, CLI en tijdelijke agentkeys vallen onder dezelfde controle.

04

Geld- en tokenbudgetten

Begrens het bedrijf, een gebruiker, een aanbieder of een model per dag, week, maand, jaar of voortschrijdende uren. Alle passende plafonds gelden tegelijk.

05

Gedrag bij de grens

Weiger nieuwe verzoeken of geef bestaande sessies een beperkte afrondtijd met eventueel extra budget. Herstel via de periode, wachttijd of vrijgave door een beheerder.

06

Gebruik en modeltarieven

Bekijk kosten per gebruiker, model of aanbieder. Externe tarieven voor input, output en cache voer je zelf in. Historische tellingen behouden het oorspronkelijke tarief.

Skills & koppelingen

01

Eigen skills en SKILL.md

Gebruik meegeleverde werkwijzen, maak eigen instructies of importeer een SKILL.md. Stel de beschikbaarheid per repository in; een skill geeft geen extra rechten.

02

MCP-registry en eigen servers

Voeg toegestane tools toe, test een koppeling en schakel die uit of verwijder die. Selecteer per taak welke koppelingen de agent krijgt.

03

Meldingen en gebeurtenissen

Stel per repository e-mail of Slack-, Teams- en Mattermost-webhooks in. Meld klaar voor review, mislukken of mergen, met status en zonder meegestuurde code.

04

Webzoeken en netwerk

Webzoeken is per box of taak te regelen. De zoekvraag gaat naar buiten. De agent kan toegestane internetdiensten gebruiken terwijl het interne netwerk wordt afgeschermd.

05

Eigen Git-server

Verbind GitHub, GitLab of Gitea, ook met een eigen certificaat. Toegang en webhooks worden passend ingericht voor jullie netwerk en Git-omgeving.

06

Maatwerk van AITJE

Geïnstalleerde uitbreidingen hebben eigen toegang, instellingen en dagmaximum. Schrijvende maatwerkformulieren vragen bevestiging. Ontwikkeling en koppelingen worden apart begroot.

Beheer & continuïteit

01

Systeem en modelkeuze

Regel het standaardmodel en de capaciteit voor agenttaken. De lokale beheerconsole blijft ook bij storingen beschikbaar. De box start na een stroomuitval weer op.

02

Back-up en herstel

Een nachtelijke databaseback-up, standaard 14 dagen bewaard. Gemiste back-ups worden ingehaald. Handmatig back-uppen en herstellen kan via de beheerhulpmiddelen.

03

Updates en herstelpad

Updates gebruiken een ondertekend manifest en een gezondheidscontrole. Bij een ongezonde nieuwe versie kan de box naar de vorige terug.

04

Logboek en bewaartermijnen

Beheerhandelingen komen in het auditlog. Gedetailleerde agent- en sessiegegevens hebben een bewaartermijn; inhoudsloze kostentellingen blijven langer bewaard.

05

Support en telemetrie

Jullie bepalen de toegang voor support op afstand. Gebruikscijfers delen staat standaard uit. Diagnostiek en een optionele handmatige gezondheidsmelding helpen bij onderhoud.

06

Afscherming en begrenzing

Agentwerk draait in een container met CPU-, geheugen- en schijflimieten. Geheimen zijn versleuteld opgeslagen. Een waakhond helpt vastgelopen diensten te herstellen.
